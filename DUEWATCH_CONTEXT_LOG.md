### 2026-08-13 — Claude Code — Post-2A.1 execution safety checkpoint: Autopilot at-most-once auto-send (candidate, not merged)

**Base:** `51ee89d329ff1a76a43f3236b190d2deb0940940` (canonical `main` post-merge). Branch: `claude/autopilot-execution-idempotency`.

**Why this checkpoint exists:** Phase 2A.1's second and third review-fix passes each independently discovered the same pre-existing defect and explicitly deferred fixing it: `autopilot-scheduler/index.ts`'s auto-send path never wrote an `awaiting_signature` row, so `handledKeys` (built only from `awaiting_signature`) could never reflect an auto-sent reminder — the same, often first/lowest-`sort_order` rule could keep winning `planRun()`'s selection forever, and worse, nothing in the system prevented a genuinely concurrent scheduler invocation (overlapping cron + manual dispatch, or two overlapping cron firings) from both deciding an invoice/rule pair was unhandled and both calling Resend. This checkpoint proves **at-most-once automatic execution** (not exactly-once delivery, which Resend's own retry/delivery behavior is outside Duewatch's control over) and, as an explicit consequence of fixing `handledKeys`' source of truth, resolves the "first rule forever" defect as well.

**Why existing tables were not reused (stated before writing any code, per instruction):**
- `awaiting_signature` — `unique(user_id, invoice_id, status)` is scoped to the review-queue lifecycle; the auto-send path never wrote a row there at all, so it structurally cannot record an auto-sent execution.
- `events` — append-only activity log with no unique boundary on `(user_id, invoice_id, rule_id, action_type)`; `reminder_sent` rows are written *after* the Resend call, not before, so it cannot serve as a pre-send claim gate.
- `autopilot_runs` — one row per scheduler cycle, not per invoice/rule/action; no relevant uniqueness dimension exists on it at all.

**Durable claim mechanism:** new table `public.autopilot_execution_claims` (migration `20260813161329_autopilot_execution_claims.sql`) with `unique (user_id, invoice_id, rule_id, action_type)` and a new SECURITY DEFINER function `public.acquire_autopilot_execution_claim(p_user_id, p_invoice_id, p_rule_id, p_action_type, p_idempotency_key)` that does `INSERT ... ON CONFLICT (user_id, invoice_id, rule_id, action_type) DO NOTHING RETURNING id`, falling back to a `SELECT` of the existing row when the insert affects zero rows — the exact atomic-claim pattern already proven for `start_import_run` (Phase 1.5B, Blocker 8). Exactly one caller ever gets `acquired = true` for a given identity, for the lifetime of the table; every other caller (concurrent, or any later scheduler run, regardless of the existing row's `status`) gets `acquired = false` and must not attempt the external send. `rule_id` deliberately has **no** foreign key: `autopilot_rules` is a real hosted table (per `src/lib/autopilot.js`'s own header comment) but its DDL was never tracked in this repo's migrations/schema.sql, so a disposable local Postgres instance has no such table to reference — the composite unique constraint on stored uuid columns is the real identity boundary and does not depend on that FK. `acquire_autopilot_execution_claim` additionally verifies `p_invoice_id` actually belongs to `p_user_id` before ever inserting (defense-in-depth; this is a trusted service-role-only function, but Phase 2A.1's doctrine of structurally verifying tenant ownership rather than trusting inputs was reused here). Privileges follow the Phase 1.5B privilege-baseline convention exactly: explicit revoke-all then narrow grants (service_role: `select` + column-scoped `update(status, provider_message_id, evidence, resolved_at)` only — no `insert`/`delete`, since inserts only ever happen inside the SECURITY DEFINER function and rows are never deleted; authenticated: `select` only, RLS-scoped to `auth.uid() = user_id`; anon/PUBLIC: nothing), verified by a migration-embedded postcondition `DO` block.

**Uniqueness identity:** `(user_id, invoice_id, rule_id, action_type)` exactly as specified — no scheduler run id, no date/time, no random uuid, no rule snapshot hash. `action_type` is `'send_reminder'`, matching the existing `awaiting_signature.action_type` vocabulary. A new pure module `supabase/functions/_shared/executionClaim.js` (no Deno/Supabase imports, runs identically under Node and Deno, same convention as `_shared/rules.js`) builds this identity (`buildExecutionIdentity`) and a deterministic string representation (`buildIdempotencyKey`) — plain concatenation of the four identity fields with a fixed prefix, not a hash, since every component is already a fixed-format uuid or short fixed vocabulary and human-readability/debuggability was preferred over inventing a second hashing scheme alongside `nextActionAuthority.js`'s rule-snapshot fingerprint. Because the identity is built only from `rule_id` (never rule content), editing a rule's tone/trigger_days in place after it has already executed cannot manufacture a fresh identity — proven directly (a test computes the identity twice with the same `ruleId` and asserts equality, standing in for "before/after edit").

**Provider idempotency:** `supabase/functions/_shared/resend.js`'s `sendEmail()` gained one new optional parameter, `idempotencyKey`, which sets the `Idempotency-Key` HTTP header when supplied; callers that don't pass one (there are none left in this codebase, but the parameter stays optional rather than required) get Resend's normal behavior, unchanged. Explicitly secondary protection only — the database claim remains authoritative, per instruction, since Resend's own idempotency-key retention window is bounded and outside Duewatch's control.

**Failure/uncertainty semantics:** the scheduler's auto-send path in `actOnMatch()` (`autopilot-scheduler/index.ts`) now follows the required order exactly: candidate/rule/invoice already established by `planRun()` → local precondition (`to` exists; the no-email fallback path is unchanged, makes no external request, and needs no claim) → `acquire_autopilot_execution_claim` (STOP with zero writes below if `acquired` is false) → `sendEmail()` with the deterministic idempotency key, wrapped in try/catch → record the result against the *existing* claim row → only on confirmed success, write `reminders`/`invoices.last_reminder`/`events`. Three terminal claim states beyond `in_flight`: `sent` (confirmed provider success), `send_failed` (a clean HTTP response reporting a definite error — e.g. bad API key, invalid recipient), `uncertain` (an exception/network failure where whether Resend received the request cannot be proven). **All three, and a claim stuck in `in_flight` from a crash between acquisition and resolution, are structurally equivalent from a safety standpoint**: `acquire_autopilot_execution_claim` blocks reacquisition based on the row's mere existence, never its status, so none of them are ever auto-retried — this is the fail-closed behavior the instruction required, achieved by construction rather than a status-specific branch. A claim-acquisition-call failure itself (`claimError`, e.g. a transient DB error) is the one case that's safely retryable next run *without* any special-cased logic, because no claim row was ever created — noting this distinction explicitly per instruction, rather than building unrequested automatic-retry logic for it. As a direct consequence of `autopilot_execution_claims` now also feeding `handledKeys` in `runForUser()` (alongside the existing `awaiting_signature`-derived keys), the "first rule forever" defect discovered and deferred across the second and third Phase 2A.1 review-fix passes is now resolved: once an earlier rule's auto-send is durably claimed (any status), `planRun()` can no longer keep matching it, so a later, more-advanced rule becomes eligible. Also fixed as a narrowly-scoped truthfulness correction in the same touched code block (test 16's requirement): the `reminders` row and `invoices.last_reminder` update are now written only on confirmed success, not unconditionally as before — previously a failed send still recorded a "Reminder sent" reminder and bumped `last_reminder`, which `events.lifecycle_state` already correctly distinguished but the other two tables did not.
