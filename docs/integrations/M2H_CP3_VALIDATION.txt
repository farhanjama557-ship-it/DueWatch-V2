IDENTITY / MODE
  Connection context supplies authenticated DueWatch tenant, expected Stripe
  account and exact test/live mode. Payload never chooses tenant. Event account
  and mode are validated before any obligation. Connected-account events must
  name the expected account. Frozen CP1 has no separate mode field, so CP3
  binds mode into CP1 providerAccountId as <acct>:test or <acct>:live. A test
  observation presented to a live expected connection is rejected by CP1 as a
  provider-account mismatch. Object and subject identities are mode-scoped too.

TRUTH DIMENSIONS
  Invoice maps to T1 only. Non-succeeded PaymentIntent and uncaptured Charge
  map to T2. Succeeded PaymentIntent and captured successful Charge map to T3,
  sharing one receipt subject when related. InvoicePayment maps to T4.
  Self-reported/custom PaymentRecord remains T2; guarded Stripe-reported,
  Stripe-processor guaranteed value can map T3. Credits/customer balances map
  T4. Refund/Dispute are T3 reversal/contest context and reopen no AR by
  inference. BalanceTransaction/Balance/Payout map to T5. T6 is unsupported.

EVENTS / PAGING
  Events are scope-checked invalidation evidence only. Every obligation says
  stateWrittenFromEvent=false and requires authoritative account+mode-scoped
  rereads. Parsed fixture JSON is not raw wire bytes and cannot be called
  signature-authenticated. CP6 owns signatures, delivery/retry durability and
  lifecycle. Paging requires explicit has_more and a terminal page; failure,
  malformed metadata or an incomplete embedded Invoice payments list remains
  incomplete. Duplicates are idempotent and older versions cannot win.

EVIDENCE / SANDBOX
  Current official Stripe API and webhook sources were inspected. E1/E2/E3 are
  used only where same-provider proposition evidence supports them; E7 needs
  support-bearing evidence from multiple providers. No Stripe sandbox
  credentials were available and no live API call was made. E4/E5/E6 remain
  unclaimed. Fixture replay is not sandbox evidence.
