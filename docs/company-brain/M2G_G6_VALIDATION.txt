==================================================
3. ARCHITECTURE SUMMARY
==================================================

G6 adds one deterministic kernel, one presentation adapter, one persistence
loader, one founder-facing surface, and one migration.

  founderReview.js             pure domain kernel: review-item derivation,
                               durable review decisions, current-state
                               derivation, read models
  founderReviewPresentation.js pure view shaping (no React, no I/O)
  founderReviewLoader.js       tenant-scoped Supabase reads + delegation to the
                               owning RPCs (G6 review, G5 grant, G5 revoke)
  CompanyBrainReview.jsx       founder surface (read-and-decide only)
  CompanyBrain.jsx             /company-brain route

Review items are derived from frozen upstream state, never invented:
  G4 operating model  -> understanding, policy, role and delegation items
  G3 durable conflicts + G4 blockers -> conflict items
  G5 authority read model            -> authority-state and proposal items

A single derivation core is shared by the store-backed entry point
(buildFounderReviewItems) and the persistence-backed entry point
(buildFounderReviewItemsFromRecords); test G6-R6 asserts the two produce
byte-identical output, so there is exactly one derivation engine.

4. DOMAIN SEMANTICS
==================================================

REVIEW ITEM MODEL (structured, never free text):
  reviewKey, tenantId, category, itemType, subjectType, subjectId, subject,
  proposition, proposedValue, why, scope, clientId, roleId, confidence,
  conflictStatus, conflictKeys, unresolvedReason, evidence, claims,
  supportingSourceRevoked, subjectFingerprint, reviewableActions,
  resolutionPath, authorityImpact, authorityProposalId, authorityGrantId,
  authorityStatus, temporalState, operatingState, policyResolutionStatus,
  sourceStatementIds, generatedAt, asOfDate, boundaries.

REVIEW ITEM TYPES:
  UNDERSTANDING, POLICY_OR_RULE, CONFLICT, OPERATING_MODEL,
  ROLE_OR_RESPONSIBILITY, DELEGATION, AUTHORITY_PROPOSAL, AUTHORITY_STATE,
  STALE_OR_CHANGED_ITEM.

REVIEW STATUSES:
  PENDING, APPROVED, EDITED, REJECTED, HELD, DEFERRED, SUPERSEDED, STALE,
  REVIEW_REQUIRED.

REVIEW ACTIONS AND WHERE THEY ARE OFFERED:
  understanding / policy / role / delegation  APPROVE EDIT REJECT HOLD DEFER
  conflict                                    HOLD DEFER only
                                              (resolution path = G3 founder decision)
  authority proposal                          EDIT REJECT HOLD DEFER only
                                              (no APPROVE: it would read as a grant)
  authority state                             no G6 review action at all
                                              (mutation path = G5 grant / revoke)

REJECT semantics: refuses the proposition, never asserts its inverse.
Every revision carries assertsInverseProposition = false and
inferredOppositeValue = null (test G6-X).

HOLD / DEFER: distinct statuses, both unresolved, neither counted as reviewed
understanding and neither able to become a silent default (G6-Y, G6-Z, G6-R9).

==================================================
5. AUTHORITY SEPARATION GUARANTEES
==================================================

The core distinction is enforced in four independent places:

 1. Kernel:      every review revision is constructed with
                 authorityGranted: false, authorityImpact: 'NONE',
                 canonicalMoneyMutated: false, executed: false.
 2. Store shape: FounderReviewStore holds no authority handle. It has no
                 grantAuthority, revokeAuthority or evaluateAuthority method
                 (asserted by test G6-BJ).
 3. Input guard: recordReviewDecision rejects any request carrying an
                 authority field — explicitGrant, grantAuthority, grantee,
                 grantId, approvalRequirement, effectiveWindow,
                 authorityAction, authorityScope, limits, channel,
                 revokeAuthority, isFounder, founderId, tenantOverride,
                 authorityGranted — rather than ignoring it (G6-Q, G6-R).
 4. Database:    company_brain_founder_review_revisions_g6 declares
                 authority_granted boolean not null default false
                   check (authority_granted = false)
                 and the same pattern for authority_impact,
                 asserts_inverse_proposition, resolves_conflict,
                 canonical_money_mutated and executed.

Standing DW authority is created ONLY by the pre-existing G5 path:
  AuthorityDelegationStore.grantAuthority (explicitGrant === true, founder /
  tenant-owner actor) and public.grant_company_brain_authority_g5.
G6 defines no grant semantics. founderReviewLoader.requestAuthorityGrant is a
pass-through that requires every G5 dimension explicitly and refuses a missing
one rather than defaulting it, so an omission can never widen to a wildcard.

==================================================
6. CONFLICT INTEGRATION (G3)
==================================================

G6 builds no second conflict-resolution engine. Conflict items project the
durable G3 conflict records (every competing claim, its scope and its
preserved value) plus G4 blockers, and read founder-decision coverage through
deriveFounderDecisionState. Resolution goes through
CompanyBrainDurableStore.recordFounderDecision. Losing evidence is preserved
and still rendered after a decision (G6-BX). No conflict is ever reduced to a
confidence score; confidenceResolved is false on every conflict item.

==================================================
7. OPERATING MODEL INTEGRATION (G4)
==================================================

Every G4 statement across the ten sections plus client overrides becomes one
review item carrying its state, temporal state, policy resolution status,
conflict keys, explanation, provenance and confidence. Approving an operating
statement records a review decision and nothing else (G6-B).

==================================================
8. G5 INTEGRATION
==================================================

getAuthorityReviewState is a projection of the G5 read model. It adds no
capability: current, proposed, revoked, stale, superseded and invalidated
authority all come from deriveAuthorityState. Authority cards render all nine
G5 dimensions by name — ACTION, SCOPE, CLIENT, AMOUNT, CURRENCY, CONDITION,
TIME, CHANNEL, APPROVAL — and an unspecified dimension renders as
"Not specified — no authority is implied" (G6-U5).

==================================================
9. FRESHNESS SEMANTICS
==================================================

Each item carries a subjectFingerprint over exactly what the founder reviewed
about THAT item: its proposition, proposed value, conflict state, operating
state, policy status, temporal state, and its own evidence and claims. A
review revision cites the fingerprint it saw.

  fingerprint unchanged  -> the recorded status stands
  fingerprint changed    -> REVIEW_REQUIRED / SUBJECT_CHANGED_SINCE_REVIEW
  supporting source revoked -> REVIEW_REQUIRED / SUPPORTING_SOURCE_REVOKED
  reviewed subject gone  -> REVIEW_REQUIRED / REVIEWED_SUBJECT_NO_LONGER_PRESENT

There is no global invalidation. An unrelated ingestion leaves unrelated
approved items approved (G6-AF), while a revocation that actually feeds an
item does affect it and only it (G6-AE). Authority freshness is untouched by
G6 and stays governed by the G5 reviewed-dependency fingerprints (G6-AH).

==================================================
10. SUPERSESSION AND NO RESURRECTION
==================================================

Each accepted review decision appends a revision that explicitly names its
predecessor via supersedesRevisionId. The current revision is the newest
unsuperseded tip. When that tip is stale against a changed subject the item
becomes REVIEW_REQUIRED — the superseded predecessor never returns as current
truth (G6-AC, G6-AD). History is append-only and deeply frozen; an earlier
decision cannot be overwritten (G6-BD).

==================================================
11. IDEMPOTENCY AND STALE WRITES
==================================================

Same idempotency key + same semantic request -> the same revision returned,
no second row. Same key + different request  -> rejected with an audited
REJECTED_IDEMPOTENCY_CONFLICT. Distinct revisions with distinct values stay
distinct (G6-AM, G6-AN).

Two independent stale-write guards, both fail-closed and both audited:
  expectedRevision  != stored revision count -> REJECTED_STALE_REVISION
  subjectFingerprint != current item fingerprint -> REJECTED_SUBJECT_CHANGED
Newer truth is never silently overwritten (G6-BW). The RPC enforces the
revision guard server-side as well.

==================================================
11b. INDEPENDENT AUDIT FIX PASS
==================================================

An independent review of the first G6 commit raised three findings. All three
were real. This is what was wrong and what changed.

FINDING 1 — the stale-subject guarantee trusted the caller.
  Confirmed. record_company_brain_founder_review_g6 only regex-checked the
  FORMAT of p_subject_fingerprint and then stored it. It never compared it
  against anything, so at the database layer a caller could assert any subject
  state it liked. Only the in-process JS kernel compared fingerprints.
  Fixed: staleness is now decided by the server from its own tables.
    - The review item row carries a server-owned current_subject_fingerprint
      and the upstream derivation it was built from.
    - Every review must cite an upstream binding (G4 operating model row, G3
      conflict, G5 proposal or grant); an unbound review is refused, because
      there would be nothing server-owned to check against.
    - The server re-reads the cited G4 row and rejects the write unless its
      model_fingerprint matches AND its status is still PROPOSED or BLOCKED.
    - It re-reads the cited G3 conflict and rejects a moved revision.
    - It re-reads the cited G5 grant and rejects one no longer GRANTED.
    - Under an unchanged derivation, the stored subject fingerprint is the only
      acceptable one; a caller claiming a different subject state is refused.
  Proven by execution: G6-RT4, RT5, RT6, RT7, RT8.

FINDING 2 — rejected attempts were rolled back by the raise that followed them.
  Confirmed, and it is exactly the PostgreSQL semantics the reviewer suspected:
  the REJECTED_STALE_REVISION audit row was inserted and then destroyed by the
  `raise exception` in the same transaction, so rejected stale writes left no
  trace at all.
  Fixed: rejections now RETURN an outcome instead of raising, which is also the
  pattern the existing idempotency-conflict path and the G5 RPC already used.
  The audit row commits; the mutation still fails closed because no revision
  row is written and the client treats any outcome other than ACCEPTED or
  IDEMPOTENT_REPLAY as an error (submitFounderReviewDecision throws).
  `raise` is kept only for unauthenticated and malformed calls, which write
  nothing and have no founder decision to audit.
  A concurrent revision collision is caught by an `exception when
  unique_violation` handler that audits from inside the handler, which runs
  after the failed statement is rolled back, so that audit row also survives.
  Guards were also reordered so a rejected call can no longer bring a review
  item row into existence: the item is read, not upserted, before the checks.
  Proven by execution: G6-RT3, RT9, and the shape pinned by G6-M11/M11b.

FINDING 3 — the production surface lost conflicts and evidence.
  Confirmed, and worse than a metadata gap: loadFounderReviewReadModel passed
  conflicts: [] and empty knowledge, so /company-brain would have rendered ZERO
  conflicts for a tenant with unresolved ones, and every item's evidence would
  have looked absent — which the derivation reads as revoked support.
  Fixed by wiring the reads that were missing. Every required table already
  exists and is already owner-readable by `authenticated`, so no dependency was
  missing and nothing had to be invented:
    company_brain_conflicts, company_brain_conflict_members,
    company_brain_claims, company_brain_claim_roots, company_brain_sources,
    company_brain_source_versions, company_brain_source_tombstones.
  A conflict is treated as resolved only when the conflict row itself says so
  and names the founder decision that resolved it; G6 does not re-derive
  founder-decision validity, which remains G3's to decide.
  A read that fails now fails the whole load, because rendering a partial
  Company Brain would understate conflicts and overstate freshness.
  Proven by G6-L1..L11, which reproduce the store-backed items from persisted
  row shapes and assert the two derivations agree exactly. G6-L3 and G6-L5 pin
  the regression itself by showing what the empty inputs used to erase.

THREE DEFECTS FOUND BY THIS PASS THAT THE REVIEW DID NOT RAISE:
  a. Competing conflict positions were ordered by store insertion order, which
     persisted rows cannot reproduce (conflict_members has no ordering column).
     They are now ordered by claim id so both derivations agree.
  b. Tombstones were keyed by source id while evidence is keyed by source
     version id, so the tombstone check could never match. It now accepts
     either keying and the loader resolves a tombstoned source to its versions.
  c. The authority-proposal mapper read row.scope and row.proposed_configuration,
     neither of which exists on company_brain_authority_proposals. It now reads
     action_class and authority_scope, and leaves the dimensions it has no
     column for as "not specified" rather than inventing them.

12. TENANT ISOLATION
==================================================

Every kernel entry point asserts the authenticated actor's tenant. Items are
filtered by tenant BEFORE aggregation, never after. Cross-tenant reads,
mutations, grants and revocations all raise (G6-S, G6-T, G6-U, G6-V, G6-W,
G6-BF). The founder test is identical to G5's: authenticated, role FOUNDER,
and actor.id === tenantId — G6 does not widen who counts as a founder.
Persistence follows the repository RLS convention: user_id on every row,
RLS enabled, owner-read-only policies, all write privileges revoked from
public/anon/authenticated, mutation only through a security-definer RPC that
derives the tenant from auth.uid().

20. KNOWN LIMITATIONS
==================================================

 1. No prior gate wired the Company Brain to Supabase at runtime, so the
    /company-brain route reads durable G5/G6 rows and the persisted G4
    operating-model payload, and renders the legitimate empty state for a
    tenant with nothing stored. No sample or placeholder data is shown. The
    ingestion/persistence pipeline that populates those tables in the running
    app is not part of G6.
 2. RESOLVED by the audit-fix pass. The loader now reads the G2 sources,
    source versions, claims, claim roots and tombstones, and the G3 conflicts
    and conflict members, so the record-backed derivation carries the same
    evidence, freshness and conflicts as the store-backed one (G6-L1..L11).
 3. Editing an authority proposal is recorded as an inert G6 review revision.
    Materialising the edited proposal as a new G5 proposal row is left to the
    gate that owns proposal generation. Relatedly,
    company_brain_authority_proposals has no proposed-configuration column, so
    a proposal's amount, currency, condition, time, channel and approval
    dimensions render as "not specified" rather than being invented. Storing a
    full proposed configuration belongs to the gate that generates proposals.

 6. The runtime RPC suite needs a PostgreSQL server it can create (initdb plus
    a `postgres` user, or G6_TEST_PG_SOCKET pointing at one). Where neither is
    available it skips and prints a warning, and the executed guarantees in
    section 11b are then unverified for that run.
 4. The G6 review RPC IS now exercised against a live PostgreSQL 16.13
    instance, but only against a stub of its upstream schema (see 14 and 19).
    Its behaviour against the real G1/G4/G5 tables is still unproven.
 5. HOLD and DEFER are distinct statuses with distinct semantics but the same
    storage shape, as permitted by the specification.
